# Phase 2 — the schema engine

**Goal:** `Humcp.Schema` in full — all three tiers, `$ref` resolution with cycle detection,
validation, description sanitisation, and a harvested corpus with golden tests. No UI work
(ROADMAP §10).

**Exit:** ≥90% of corpus parameters render at Tier 1 or 2; every schema produces *something*.

**Status: complete.** 95.0% of real-world top-level parameters render at Tier 1 or 2, and 91.2% at
Tier 1 alone. Every one of the 213 harvested schemas produces a form. 813 automated tests green.

The corpus is the phase's real product. Everything below that reads as a decision was checked
against it first.

Environment: .NET SDK 10.0.400, Windows 11 (10.0.26340), `ModelContextProtocol.Core` 2.2.0,
`JsonSchema.Net` 9.4.0 (new this phase), xunit.v3 3.2.2.

## 1. What exists

```

├─ FieldModel.cs           FieldKind, FieldTier, the neutral field
├─ FormModel.cs            a whole set of inputs
├─ FieldConstraints.cs     limits, and how to say them out loud
├─ ChoiceOption.cs         label and value, kept apart
├─ FormBuilder.cs          the tiering engine
├─ SchemaResolver.cs       $ref, locally only, with cycle detection
├─ SchemaValidator.cs      JsonSchema.Net in, sentences out
├─ ValidationReport.cs     advice, never a veto
└─ (Phase 1) TextSanitizer, NameHumanizer, OperationSafety

tests/fixtures/schemas/    the corpus: 213 tools from 22 servers, plus a manifest
tests/fixtures/golden/     one readable transcript per server, plus coverage.txt
```

`Humcp.Core` no longer counts parameters by hand. `ToolInfo` carries a `FormModel`, built once at
listing time, and `ParameterCount` and friends are derived from it.

### The numbers

From `tests/fixtures/golden/coverage.txt`, regenerated by the test suite:

| | Tier 1 | Tier 2 | Tier 3 | Tier 1 or 2 |
|---|---|---|---|---|
| Top-level parameters (785) | **91.2 %** | 3.8 % | 5.0 % | **95.0 %** |
| Every field, nesting included (1166) | 89.6 % | 6.4 % | 3.9 % | 96.1 % |

213 tools, 12 of which take no arguments. **213 of 213 schemas can be validated against** — there is
no real server in the corpus whose schema defeats the validator entirely.

## 2. The corpus

`tools/Humcp.Harvester` starts each server in `servers.json` over a real stdio pipe, calls
`tools/list`, and writes each tool's `name`, `title`, `description`, `annotations`, `inputSchema`
and `outputSchema` into `tests/fixtures/schemas/<server>/<tool>.json`. Re-running it regenerates the
whole thing; the server list is checked in, so the corpus has provenance rather than an origin
story.

22 of 26 servers answered: everything, filesystem, memory, sequential-thinking, github, slack,
postgres, puppeteer, brave-search, google-maps, everart, playwright, context7, firecrawl, notion,
exa, tavily, kubernetes, figma, fetch, git, time.

Credentials in `servers.json` are deliberately fake. `tools/list` is metadata, and almost every
server publishes its catalogue before it authenticates anything. The four that did not answer are
recorded as failures in `manifest.json` rather than dropped — a corpus that hides what it could not
reach is not evidence. One of those failures turned out to be the most interesting thing in the
phase (2.1).

**The talking point.** Twenty-two servers, written by strangers, none of whom have heard of this
project, and 95% of their parameters land on a native control with a label, help text and a
constraint description. No per-server code exists anywhere in the repository.

## 3. Findings that change later phases

### 3.1 A published server can lose its entire tool list to one malformed schema

`@modelcontextprotocol/server-gitlab` publishes nine tools. Every one of them has this, verbatim,
as its `inputSchema`:

```json
{"$schema": "http://json-schema.org/draft-07/schema#"}
```

A dialect declaration and nothing else — a zod-to-json-schema conversion that lost the body.
`ModelContextProtocol.Core` 2.2.0 requires `inputSchema` to be an object schema and throws while
deserialising the listing:

```
The specified document is not a valid MCP tool input JSON schema. (Parameter 'InputSchema')
```

so **all nine tools are lost and the server shows as failed**. The failure is below us, in the SDK,
during `tools/list` — not somewhere the schema engine can reach.

Two consequences, and they point in opposite directions.

- **Our engine handles the schema itself perfectly well.** An object schema with no `properties` is
  a tool that takes no arguments, and that is what we render. It is wrong about GitLab, and wrong in
  the only way no client can fix: parameters a server never published cannot be recovered. The shape
  is now a named test case rather than a hypothetical.
- **One bad tool should not cost a user the other eight.** This is a hardening item, not a schema
  item, and it belongs to Phase 7: either list tools through a lower-level call and map them
  ourselves, or persuade the SDK to report per-tool. Written into §11's Phase 7 entry.

Phase 1's work is what made this diagnosable at all: the failure reason reaches the tree node, so
the server reads as *"gitlab, error: The specified document is not a valid MCP tool input JSON
schema"* rather than as an empty branch.

### 3.2 `anyOf: [X, null]` is not a union, and treating it as one would have cost a fifth of Tier 1

The single highest-value special case in the builder. Generators spell "optional X" as
`anyOf: [{...X}, {"type": "null"}]` or as `type: ["string", "null"]`, and both are unions by the
letter of the spec. Sending them to Tier 3 would have been defensible and would have been a disaster:
the C# SDK marks *every* optional parameter this way, so every optional parameter of every C# MCP
server would have become a JSON editor.

Unwrapping is safe because the builder's simplifications never reach the validator (3.5).

### 3.3 The discriminated-union promotion would recover nothing — measured, not guessed

ROADMAP §12 argues that OpenAPI's `discriminator` promotes `oneOf` from Tier 3 to Tier 2, and that
the benefit would flow backwards to MCP's dispatch-style tools. The corpus disagrees, at least for
now.

Of the 18 top-level parameters that reached Tier 3 through a union, **zero** are a union of object
branches each pinned by a constant discriminator. They are almost all `anyOf: [object, string]` —
a structured value or a shorthand string, notion's house style — where rendering the object branch
would silently hide the shorthand.

So the promotion is not built, and §5's placement of `oneOf` at Tier 3 stands unchanged. The number
is recorded here so the v4 planning conversation starts from evidence rather than from the
plausible-sounding argument.

The same measurement kills a smaller idea: of the 12 free-form-object parameters, **11 accept any
key at all** and only one is a typed map. A dictionary editor would recover a single parameter in
213 tools.

### 3.4 `format: date` does not appear in 785 real parameters

Not once. The formats that do appear on top-level parameters are `uri` (6), `uuid` (6), `int32` (4)
and `json` (2).

This does not reverse anything: elicitation's `requestedSchema` blesses `date` and `date-time`
explicitly (§3), so Phase 5 needs the control, and Phase 0 already accepted `DatePicker` for it.
What it says is where Phase 3's effort should *not* go. The `DatePicker` and its
<kbd>Alt</kbd>+<kbd>Down Arrow</kbd> hint (§7.15) are on a path that no server in the corpus takes,
while the plain text box is on a path 91% of parameters take.

### 3.5 The builder simplifies; the validator must not see the simplification

Stated as a rule because it is what makes the rest of the builder safe to write.

`FormBuilder` merges `allOf`, unwraps nullable unions, and infers a missing `type` from neighbouring
keywords. Every one of those is an approximation — the `allOf` merge takes the first branch's
keyword where two disagree, rather than intersecting them. None of it can produce a wrong answer,
because `SchemaValidator` evaluates the **original document**, never the builder's node. The worst
case is a control that looks more permissive than it is, and a server that says no.

The alternative — validating the simplified schema — would let a rendering convenience quietly
change what counts as a valid call. That is the one thing a client must not do.

### 3.6 Assertion semantics are a conformance surface; wording is not

`JsonSchema.Net` 9.4.0 is the first package `Humcp.Schema` has ever referenced, and the reasoning is
worth keeping. A hand-rolled subset validator would disagree with the server about what is valid,
and an over-strict client makes a working tool unusable (§5) — so the assertion semantics are worth
a dependency. The messages are the opposite kind of problem: they are read aloud to someone who
cannot see which box turned red, and `Required properties ["owner"] were not present` is not a
sentence. Every message humcp shows is written here.

Three settings turned out to matter, and each was found by listening to what the output would have
sounded like:

- **`IncludeApplicatorErrors = false`.** Without it, one bad value three levels down is also
  reported against the object above it, and again above that. The user hears the same problem three
  times and only the innermost one names the field.
- **`required` is split per missing property.** The library reports it against the object that is
  missing something, which points at the group rather than at the empty box — and §7.8 moves focus
  to the first invalid *field*.
- **A list entry is named by its list and its position.** "Tags, entry 2", not "Item", which is what
  every row of every list is called.

One library defect worked around: in 9.4.0 both `SchemaLocation` and `EvaluationPath` come back with
a duplicated final segment for a value inside an array (`/properties/tags/items/items`), so a
pointer built from either resolves to nothing. Nothing breaks — it is only the route to a nicer
sentence — but the validator finds the failing keyword's value through the field model instead, and
walks the schema alongside the instance path when there is no field model to ask.

### 3.7 A schema is a third-party document, so validation must not open a socket

`JsonSchema.Net` resolves `$ref` through a registry with a fetch hook. Left at its default that hook
is `SchemaRegistry.Global`'s, and a `$ref` to `https://attacker.example/` would make *opening a
form* an outbound request to an address a third-party server chose.

The validator uses its own `SchemaRegistry` with `Fetch` pinned to return null, rather than reaching
into the shared static to make that decision for everybody. `SchemaResolver` refuses non-local
references for the same reason and reports them: "an external reference to …". Both are covered by
tests that would hang rather than fail if the behaviour ever regressed, which is the tell.

### 3.8 Recursion off the wire is not the textbook shape

The C# SDK inlines a nested type rather than putting it in `$defs`, and spells recursion as a
pointer into the schema's own property tree:

```json
"child": { "$ref": "#/properties/tree/properties/child" }
```

Cycle detection tracks the pointers currently being expanded along one branch, so this is caught two
levels below where the recursion starts rather than at it. That is not a defect: the user gets two
real groups to fill in and a JSON editor under them, which is more useful than catching it earlier
would have been. It terminates, which is the property that matters.

The detection is deliberately per-branch and not per-document — two siblings pointing at the same
`$def` is the ordinary case, and demoting it would be a bad trade. Both halves have tests.

### 3.9 Enum values are left exactly as they are

Property *names* are humanised, because `list_pull_requests` is a machine's spelling of a phrase.
Enum *values* are not, because they are identifiers as often as they are words: `us-east-1`
humanised into "Us east 1" is a value nobody could type back and nothing the server would accept.
A label comes from `enumNames` when the schema supplies one, and otherwise the value speaks for
itself.

## 4. Decisions taken

| Decision | Why |
|---|---|
| `JsonSchema.Net` 9.4.0 — the one dependency `Humcp.Schema` takes | 3.6. Assertion semantics are conformance; the messages stay ours. It is neither an MCP dependency nor a UI one, so §6.1 hedge 1 is intact |
| `ToolInfo` carries a `FormModel`, not a `JsonElement` | Built once at listing time, which detaches the schema from the document the SDK owns and defuses a hostile schema at the edge rather than on whatever thread opens a window later |
| A tier is never a failure | There is no fourth `FieldTier` meaning "cannot render". `FormBuilder.Build` has no input for which it throws |
| Tier 3 always carries a reason, and the reason is user-facing | §7.18. It is also the telemetry §5 asks for, and it is what produced 3.3 |
| Depth and field budgets, not tuning knobs | Guards against hostile input (§9): a schema may nest a hundred deep or fan out exponentially through `$defs`. Both degrade to Tier 3 rather than hanging |
| Golden files are one readable transcript per server, not serialised objects | A diff has to be judgeable. `HUMCP_UPDATE_GOLDEN=1` regenerates and still fails the test, so a regeneration cannot pass unreviewed |
| The corpus manifest records failures | 3.1 came out of a failure line. A corpus that lists only its successes is not evidence |
| The harvester talks to the SDK directly, not through `Humcp.Core` | The corpus wants schemas exactly as servers emit them, and `Humcp.Core` sanitises everything it touches |

## 5. What Phase 2 deliberately does not do

Named so nobody mistakes an absence for an oversight.

- **No UI.** No `DataTemplateSelector`, no controls, no XAML. That is Phase 3, and `FieldKind` is
  named for the shape of the data rather than for a WPF type so Phase 3 owns the mapping.
- **No discriminated-union promotion** (3.3), no dictionary editor for typed maps, no
  `if`/`then`/`else` evaluation. All three are Tier 3, all three are measured, none of them pays.
- **No MRU history.** §4 pitfall 3's per-`(server, tool, parameter)` history needs a stable key, and
  `FieldModel.Path` is it — but the store itself is `Humcp.Core`'s and arrives with Phase 3.
- **No enum-first wizard heuristic** (§4, pitfall 4). It is a Phase 3 presentation decision; the
  model carries everything it needs to make it.
- **Nothing done about `outputSchema`.** The harvester captures it, so Phase 4 has a corpus waiting.
- **No manual screen-reader pass.** There is no new surface to hear. The nineteen-check NVDA script
  from phase1-notes §6 was not re-run, because nothing it tests changed; the Phase 3 exit is where
  it becomes due again, against generated forms.

## 6. Additions to the roadmap — proposed

1. **§5 gains the nullable-union rule** (3.2): `anyOf: [X, null]` and `type: [X, "null"]` are one
   Tier 1 field that may be left empty, not a union. Stated in the tier list, because a future
   reader looking only at "oneOf/anyOf → Tier 3" would undo it.
2. **§5 gains the validation rule** (3.5): the builder simplifies for rendering; validation runs
   against the original document, so a rendering convenience can never change what counts as valid.
3. **§9 gains the corpus's provenance**: the harvester, the manifest, and the rule that failures are
   recorded rather than dropped.
4. **§11's Phase 7 entry gains the `tools/list` hardening item** (3.1): one malformed tool schema
   currently costs the user every other tool on that server.
5. **§13 gets two answers.** The discriminated-union promotion recovers nothing in real MCP servers
   (3.3), and `format: date` never appears (3.4). Neither reverses a decision; both say where effort
   should not go in Phase 3.
