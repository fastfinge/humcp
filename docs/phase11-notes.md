# Phase 11 — The model's tool search, and summaries

v2's fourth phase (ROADMAP §11, "Built in this order"), 2026-10-21. The local model finds tools by
what the user means rather than the words they share, and summarises a long result on request.

**Status: complete.** Schema 903, Core 243, Inference 5 (three need a model), UI 88 — all green; the
NVDA pass found one defect (§4).

## 1. Decisions, taken with the developer at the start

- **Enter in the search box asks the model.** Typing still gives Phase 8's word matches at every
  keystroke; Enter, when a model is downloaded, asks it, and its three picks go to the top of the list,
  each named "…, suggested by the local model", with the word matches below and no tool listed twice.
  Down Arrow goes to the word matches without asking. With no model, Enter is what it was.
- **The model reads the tool list the first time it is asked** in a session, and again only when the
  list changes. Nothing runs at start-up. The first question says so before it starts: "It reads the
  list of 56 tools first, which takes from half a minute to a few minutes; the word matches are below
  in the meantime" — and after one reading, the time that one took.
- **Summaries are on request.** A result long enough to want one (1,500 characters of text) ends with a
  Summary part offering it, with a Summarise button; <kbd>Ctrl+M</kbd> asks from anywhere in the window.

## 2. What was built

- **`IToolSuggester`** (Core), defined now because it has its two implementations (§12):
  `LexicalToolSuggester`, Phase 8's search behind it, and `ModelToolSuggester` (Inference).
- **`ToolSuggestionPrompt`** (Core, tested): the spike's catalogue — one `server/name: first sentence`
  line per tool — and question; a parser that reads the model's ids however it dresses them (list
  numbers, backticks, bullets) and can only ever return tools that exist; a fingerprint of the
  catalogue, so a changed description is a re-read.
- **`LocalModel.PrefillAsync` / `ContinueAsync`**: read the catalogue once, then for each question
  append it, answer, and `RewindTo` the end of the catalogue. The reading is not cancellable — half a
  reading is minutes thrown away — while the question is.
- **`ResultSummary`** (Core, tested): what is sent (every text part, and structured content where it
  says something the text does not; pictures and links are not text), the spike's request, a 32,000-
  character cap that the summary declares when it bites, and the label. `GeneratedText.Label` is now
  the one label for every piece of model text, alt text included.
- **`LocalModelFeatures`** (App, was `ImageDescriber`): descriptions, the suggester, and summaries over
  the one shared model.

## 3. Measured

**Tool search on the corpus** (`ModelToolSuggesterTests`, the same 35 requests and 213 tools Phase 8
measured word matching on):

| | Right tool in the top three |
|---|---|
| Word matching (Phase 8) | 21 / 35 |
| The spike's 4B, whole catalogue | 34 / 35 |
| **Phase 11** | **33 / 35** |

The catalogue read in 36 seconds on all cores; each question then took 2–3 seconds including its
answer (the spike's half-second was to the first word). The two misses are both Kubernetes ("restart
the web deployment with more copies" → `upgrade_helm_chart`, not `kubectl_scale`). `TopThreeFloor` is
31.

**In the app**, fixture plus Playwright (56 tools): the first question took 18 seconds, model load
included; the second, under two. "How big is the browser window" → Resize browser window, Page
snapshot, Take a screenshot. "Show me what the page says" → Server information (wrong), Page
snapshot, Get console messages: right in the three, not first.

**A summary of Playwright's snapshot of Wikipedia's *Screen reader*** (1,292 lines, cut to the first
32,000 characters): two minutes, and it says it was cut. It names JAWS and NVDA for Windows, VoiceOver,
TalkBack, ChromeVox, Orca and Speakup, the graphical and command-line kinds, IBM in 1978 — and "26
languages", which is the article's language-link count read as a fact about screen readers. The label
in front of it is there for exactly that.

## 4. The NVDA pass

One defect, fixed and re-checked by ear:

- **<kbd>Ctrl+M</kbd> did nothing from a form's fields.** It was bound inside the result view, so it
  worked only with the caret in the result — and from anywhere else in the window it was silently
  nothing, the one outcome a key must never have. Both windows now bind it, and from the main window's
  search results it began summarising at once.

Heard, and fine: the first question's warning; "The local model suggests 3 tools, at the top of the
list, marked as suggested."; each pick read with ", suggested by the local model"; the Summary part
reading "Summary, by the local model … Generated by the local model, and it can be wrong: This Wikipedia
page explains screen readers…"; the cut declared at the end; a second <kbd>Ctrl+M</kbd> saying it is
already summarised, and one during a summary saying it is under way.

## 5. Not done here

- **One generation at a time.** A first catalogue reading holds the model for its whole length, and an
  image description arriving meanwhile waits behind it. Measured as acceptable at 56 tools; a user with
  hundreds would feel it.
- **The catalogue is not capped.** At 213 tools it is about 4,000 tokens; the reading time grows with
  it, and nothing yet stops a very large one.
